# Performance Baselines

Roadmap M9.5. What a fixed set of scenes costs in the desktop game runtime, recorded so that a later phase can show it did not
make them slower or bigger. The numbers are in [`performance/baseline-windows.tsv`](performance/baseline-windows.tsv); the
milestone report is [`reports/m9-5-performance-baselines.md`](reports/m9-5-performance-baselines.md).

## When to run it

- **Before and after each phase or milestone that touches rendering, loading, physics, terrain or sound.** Record before
  starting, then compare after. R3's scatter tools (M3.6) and the landscape conversion (M3.10) are the next such work.
- **Only on the machine the baseline was recorded on.** Frame times depend on the GPU and driver; comparing two machines
  measures the machines. Another machine records its own file (`baseline-linux.tsv`, `baseline-macos.tsv`).
- **On a quiet machine, with each game window left on screen.** A minimized window stops rendering; the runner gives up on a
  run after 5 minutes and fails.

## How

```bash
# The large map (1025 x 1025 terrain, roadmap M3.8) is generated by a test; once per checkout
./gradlew :engine-desktop:test --tests "*LargeTerrainMapTest"

# Record: every scene 3 times in a fresh game runtime, medians to engine-desktop/build/perf/current.tsv
./gradlew :engine-desktop:perfBaseline
# Options: -PperfOut=<file>, -PperfRuns=<n>, -PperfScenes=samples/a.json,samples/b.json (a subset, no large map)

# Compare with this OS's baseline in docs/performance; exit 1 and a list when something regressed
./gradlew :engine-desktop:perfCompare
# Options: -PperfBaselineFile=<file>, -PperfCurrent=<file>

# Replace the baseline (only when a change is meant to cost more, or on new hardware; say why in the report)
./gradlew :engine-desktop:perfBaseline -PperfOut=$PWD/docs/performance/baseline-windows.tsv
```

One scene by hand: `GDXUNITY_PERF_REPORT=<file.tsv>` on any `--smoke-test` run of the game runtime appends that run's row
(and prints it as `Performance: ...`).

## What each column means

| Column | Meaning |
|---|---|
| `parseMs` | Reading and parsing the scene file. Includes loading the serializer classes, since every run is a fresh JVM: this is what a player waits for |
| `startMs` | Starting the session: scripts, 2D and 3D physics (Jolt's native library), play profile, graphs, animators, sound binding (songs and clips are read here) |
| `firstFrameMs` | Creating the renderers and drawing the first frame, which loads the models, textures, materials and terrain the scene shows |
| `frameMeanMs`, `frameP50Ms`, `frameP95Ms`, `frameMaxMs` | One frame's cost, from the start of the frame until the GPU has finished it (`glFinish`, so vsync does not hide it), over the frames after the 30 warm-up frames. The 95th percentile shows stutter the mean hides |
| `terrainTriangles` | Terrain triangles drawn per frame, on average (0 without terrain) |
| `heapPeakMb` | The largest Java heap use seen at the end of a measured frame. Not compared: it depends on when the collector last ran |
| `heapRetainedMb` | Java heap still in use after a garbage collection on the last frame: what the scene keeps |
| `audioLatencyMs` | Buffered sound latency: the sound device's own buffers (`AudioDevice.getLatency()`) plus one 512-frame block of the output. What the configuration implies, not a measurement at the speakers. `-` when the scene opens no sound device |
| `audioBlockMs`, `audioBlockMaxMs` | Mean and longest time to render one block of sound; one block lasts 11.6 ms, so a block that takes longer makes the sound drop out |
| `gpu` | The OpenGL renderer string |

## What counts as a regression

`perfCompare` reports a value that grew by more than **25 %** and by more than a floor below which run-to-run noise is
larger than the change: parse 10 ms, start 25 ms, first frame 50 ms, frame mean and median 0.5 ms, frame 95th percentile 1 ms,
retained heap 16 MiB, sound latency 1 ms, sound block 0.5 ms. The maximum frame and the heap peak are recorded but not compared.
A scene that is in the baseline but missing now, and a sound device that no longer opens, are regressions too.

## What is not measured

- **Native memory.** Meshes, textures and Jolt's bodies live outside the Java heap; there is no portable way to read a
  process's resident memory from Java. The heap columns are the Java heap only.
- **Sound at the speakers.** The latency is what the buffers imply. Underruns are not detected; the block render times show
  whether rendering keeps up.
- **The editor and the web players.** Only the desktop game runtime is measured. Editor scene loading, the Babylon player and
  the TeaVM build (which does not compile, see [`BACKEND_SUPPORT_MATRIX.md`](BACKEND_SUPPORT_MATRIX.md)) have no baseline.
- **Linux and macOS.** No machine here; the commands are the same.
