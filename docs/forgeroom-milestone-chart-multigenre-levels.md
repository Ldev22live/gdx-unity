## 1. How to read this chart

**Milestone ids** are `M<phase>.<n>`, for example `M3.3` is the third milestone of phase R3. A milestone is the smallest piece that can be started, tested, reported and called done on its own. Each ends with a report in `docs/reports/` (AGENTS.md §10).

**Size** is a guess, one person: **S** under 2 weeks, **M** 2 to 6, **L** 6 or more. They are not measured estimates.

**Status** uses the AGENTS.md §9 words, and only for things seen in this repository on 2026-11-14:

| Status | Meaning |
|---|---|
| Not started | No code or document for it exists (per the roadmap's own baseline, §3; not re-audited here). |
| Partly built | Some of it exists, listed in the notes; the milestone's done-when is not met. |
| Implemented | Code exists and has automated tests. |
| Integrated | Reachable from the editor or runtime by a user. |
| Validated | Integrated and checked in the running application by a person or an observed session. |

Nothing below is marked **Validated** as a whole. Where an observed editor session (2026-11-14, trace file) saw an operation work, the note says exactly what was seen.

**Gate** says what the owner must approve first: **TD** (a technical decision record), **Module** (a new Gradle module, AGENTS.md §4), **Dep** (a new dependency), **Legal** (asset licensing or provider terms), **Owner** (a decision in §9).

**Editability matrix statuses (Appendix F5).** The sample-to-template matrix does not use the words above. It marks each sample and each domain it actually uses as **PASS**, **FAIL**, **BLOCKED** or **NOT APPLICABLE**, with an evidence link. A missing editor, a missing source or hardcoded-only behaviour is FAIL, never NOT APPLICABLE.

**UX gate (every milestone of R0 to R9).** Appendix E5 makes this mandatory: a milestone is not accepted because the engine API works. It also needs observed manual UX checks for discoverability, low clutter, context, consistency, a short path (World, select, Customize, edit, Back to World, Play), persistence, accessibility, performance and honest status. Manual validation is recorded as pending if no graphical application was run, and a screenshot mock-up is never called an implemented UI. See rule 9 in §10.

### Proposed cross-profile extension (requires owner approval)

**RG — Genre-independent world and runtime conversion** is a proposed cross-cutting track, not a replacement for R3b/R3c. Its goal is to author one persistent 3D world through an isometric editor view and test it under different supported gameplay profiles without duplicating the scene. **Editor camera orientation, gameplay dimension, and gameplay genre are independent concepts.** See §6a for proposed milestones.

**Scope distinction:** MG.1–MG.7 prove **one scene, multiple test profiles**. MG.8–MG.11 prove **one game, multiple levels, each with its own gameplay profile**. They are separate capabilities: scene-level testing is not evidence that cross-level genre transitions work. Level-specific profile selection is the first target; switching profiles within a single level or region is a **future extension**, not an implied requirement or a claim of existing support.

**Acceptance boundary:** a different camera alone does not make a different genre. The runtime must apply the chosen profile's movement, input, collision, camera and gameplay rules. An arbitrary 3D map is not automatically a valid side-scroller: missing playable surfaces, movement plane, occlusion configuration, spawn or collision must be reported with actionable validation. Existing M3b.3, M3c.3 and M3c.8 provide related capabilities but do not by themselves prove the full **same-scene, cross-profile** journey. Existing 33-pair registry and five reported playable pairs remain historical claims, not new validation results.

## 6a. Proposed cross-cutting track RG: Author once, play through multiple genres

**Scope and status:** This track clarifies the product vision and adds acceptance criteria to existing R3b/R3c work. It is **proposed only** and must not be treated as approved implementation. Existing `GameTestProfile`, `Game Genre`, `Game Mode`, Play isolation, Platformer + 2.5D, Action RPG + 2.5D/3D, Platformer + 3D and FPS + 3D remain as reported in the original chart. Do not rename or replace those APIs without a TD and migration plan.

### Four independent concepts

1. **Editor view:** isometric, perspective, top, side or orthographic camera used for authoring. It must not determine gameplay genre or modify scene coordinates.
2. **Game dimension:** 2D, 2.5D or 3D presentation and movement constraints. A 3D-authored world may be interpreted by a 2.5D runtime where compatible; the editor must not silently convert or flatten source geometry.
3. **Gameplay profile:** the genre-specific runtime composition of camera, controls, character/unit movement, physics, navigation, combat or other rules. Unsupported combinations remain explicitly unavailable.
4. **Game and level configuration:** a game project contains multiple levels/scenes, each referencing a gameplay profile; game-wide state (such as player inventory and progression) is separate from level-local state. An editor camera is not a level genre, and changing levels must not require restarting the game.

### Architecture and safety constraints

- **One source scene, multiple runtime interpretations.** Do not create copies of the world per genre or flatten 3D objects into sprites just to change modes.
- **One game, multiple genre-specific levels.** Each level owns its scene and profile configuration; project-wide game state remains independent and survives supported level transitions. Do not mistake a camera change for a complete genre transition.
- **Transitions are lifecycle boundaries.** Deactivate old input, controllers, cameras and level-local physics before activating the new profile; preserve only explicitly designated shared state, with safe error handling.
- **Compose reusable systems.** Prefer existing camera, input, movement, collision and physics services; a profile configures these systems rather than creating a new renderer for every genre.
- **Preserve source state.** Play uses the existing isolated runtime copy. Stop restores the original editor view, selection, scene and undo history.
- **Honest capability labels.** Camera change alone is not genre support. Each advertised pair must pass movement, collision, controls, spawn and gameplay tests. RTS requires navigation, selection and commands beyond an elevated camera.
- **Desktop first, web scoped.** ForgeRoom Desktop owns full authoring. ForgeRoom Web in UrConnex may preview/play only verified supported profiles and must preserve unsupported source data under Appendix G. No parity requirement or dependency on UrConnex is introduced.
- **Approval boundary.** These are proposed milestones, not authorization to modify code, add modules or dependencies, change existing technical decisions, commit or push.

### MT: Fully editable reference templates (Appendix F)

A sample game is not a read-only showcase, a compiled demo, a video or a hardcoded engine example. It is a complete, duplicable, playable, exportable, project-owned game the user can customize through every relevant workspace. **"Fully editable" means every authored element and its available source form can be opened and changed with the matching editor**, with the limits of imported flattened content stated. **Applicability:** a 2D game need not have a 3D model to modify, and a 3D action RPG need not have a tilemap, but every feature a sample actually uses must be editable; if it has a house, terrain, a song or a combat rule, that editor and source must exist. ### WEB: ForgeRoom Web in UrConnex (Appendix G)

ForgeRoom Desktop is the complete studio; ForgeRoom Web is an UrConnex feature (Next.js front end, Spring Boot back end, PostgreSQL metadata) for easy entry, project creation, light World editing, browser preview and, where approved, sharing. **The web does not need feature parity.** Visual scripting authoring, mesh geometry editing, full animation authoring and audio or music editing are Desktop-only unless a later phase is approved. Every web capability carries an evidence-backed label: **Editable on Web**, **Preview/Play on Web**, **Desktop-only**, **Planned** or **Unsupported in this project** (G2). A browser plays desktop-authored graphs only through a tested safe interpreter, otherwise it shows a compatibility warning, and it never runs Java, Kotlin or untrusted scripts. The repositories stay separate: no desktop Java engine dependency in UrConnex, no UrConnex dependency or login for the desktop. Each WEB phase is its own approval gate.

**Where the work happens.** AGENTS.md §2 limits work here to this repository. So WEB1, WEB5 and WEB6, and the UrConnex parts of the others, belong to the UrConnex project. This repository's share is the WEB0 audit of its own Babylon web player and serializers, the desktop side of the WEB2 interchange contract (schema, unknown-field preservation, round-trip tests), and the Desktop half of the preservation tests.

## 10. Rules every milestone follows

From the roadmap's §6, in short:

1. Status words mean what §1 says; an agent that cannot see the screen writes "Manually Not Verified (Headless Environment)".
2. Tests ship with behaviour; GL-only paths are listed as needing a graphics test.
3. Editor changes are `EditorCommand`s so undo and redo work.
4. The editability audit stays green.
5. Components get a serializer and a round-trip test; asset types get a Content Browser entry, thumbnail, opening editor and drag and drop.
6. Web status is recorded for each phase, using the Appendix G2 labels (Editable on Web, Preview/Play on Web, Desktop-only, Planned, Unsupported in this project). That is a report of what works, not a parity target, and no button is shown that does nothing.
7. Each milestone ends with a report in `docs/reports/`: criteria met or not, commands, per-module test counts, limits, and a statement that no commit or push was made unless authorised.
8. **Agent parity:** a milestone that adds an editor operation adds its typed `AgentTool` and a test that drives it.
9. **UX gate (Appendix E5):** every milestone of R0 to R9 passes both its automated tests and observed manual UX checks (see §1); manual validation is pending until a person has run the graphical application, and a screenshot is not a UI.
10. **Editability gate (Appendix F5):** no template is advertised Fully Customizable until every applicable gate passes; every feature a sample actually uses must be editable; each sample and domain is PASS, FAIL, BLOCKED or NOT APPLICABLE with evidence, and a missing editor or hardcoded behaviour is FAIL; graphics and audio checks are pending until observed; partly capable samples stay available labelled Technical Demo / Partially Editable.
